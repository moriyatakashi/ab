芯と窓を分ける ba-180

芯=手で直す本物、窓=takashiの理解を進める表示。窓を源として扱うと二重管理が始まる(bjの番号衝突が実例)。

takashiのRFC像への応答 ba-180

  • run ba class shiyouは既に実装済み。新規作成でなく「既存コマンドを索引と位置づける」話
  • 「仕様の数=索引の数」の1:1は不変条件(invariant)として運用。数がズレたら棚卸しの合図
  • 「仕様の数=窓の数」の1:1は、窓を"生成"にすれば自然に達成(窓=1テンプレート×N仕様)

退役状態案(推し) ba-180

RFCのObsoleted状態のように、旧仕様を"5つ目の分類"でなく"確定仕様の退役状態"として持つ案。分類は4のまま/退役も表現でき、bjの2軸仮説(現役×退役)とも一致する。

現在のba-32との差: ba-32の現在のgistは既に「6分類(...旧仕様...記録)」という形で運用されており、この退役状態案とは異なるモデル。まだ解決されていない。

ba-180本文に「未着手・要takashi判断」と明記されている論点。

4分類か5分類か ba-180・最重要論点

ba-32規約は本来4分類のはずが、run.pyの実装とbjは旧仕様を入れて5分類。定義が実装とズレている。退役状態案を採るかどうかが鍵。
