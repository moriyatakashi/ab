ca を Firebase(Firestore)で作る

ba-242 の続き。当初はAzure Table Storage(baと同じ構成)を検討していたが、マルチAIエージェント干渉テストという目的にはFirestoreのリアルタイム更新・厳密なトランザクションの方が合うため、Firebaseで作る方針に変更。コード・インフラともにまだ何も作っていません。

対象: ab/src/ 参照: ba-242 状態: 実装未着手(計画確定・Firebase版)
置き場
01

今の ab/src/ は index.html と c1.html(このページ)の2本。フォルダは切らず、フラットに1ファイル追加します。

ab/ ├── index.html おまちください(トップ) ├── style.css └── src/ ├── index.html 既存・aaへの案内 ├── c1.html このページ ├── ca.html ← 新設(予定・ca の実体) └── ca-app.js ← 新設(予定・Firestore SDK経由のread/write)

フォルダを切らなかった理由: 現状ca.html 1枚(+ロジックのca-app.js)で足りる規模で、2ファイル目が要るタイミングで初めて分割すればよいため。aa/src/common(auth.js等)への依存は無くなる ── 認証をFirebase Authenticationに置き換えるため。

なぜFirebaseか
→

「サーバーを自分で書く」部分がほぼ消える。読み取りと人間の書き込みは、ブラウザからFirestoreへ直接アクセス(Security Rulesが認可を担う)。サーバーが必要なのは、対話的ログインができないClaudeエージェント用の鍵レーンだけ ── そこだけ小さなCloud Functionを1本立てる。

マルチAIエージェント干渉テストが目的のcaにとって、Firestoreのトランザクション(Seq採番が厳密になる)とリアルタイムリスナー(書き込みの様子がその場で見える)は直接効いてくる。

要素当初案(Azure)採用(Firebase)
データストアTable Storage(CaLog)Firestore(caThreadsコレクション、ドキュメント/サブコレクション)
読み取り経路/api/ca(Function経由)ブラウザ→Firestore直読み(Security Rules)
人間の書き込み/api/ca(Function経由、Google IDトークン検証)ブラウザ→Firestore直書き(Firebase Auth+Security Rules)
Claudeレーンの書き込み/api/ca(同じFunction、鍵は環境変数)Cloud Functions 1本(claude_key照合→Admin SDKで書き込み)
認証(人間)Google Identity Services + 自前セッションFirebase Authentication(Google Sign-Inが標準搭載)
Seq採番専用カウンタエンティティ(非厳密・ETag無し)Firestoreトランザクション(厳密・衝突しない)
ライブ更新無し(手動リロード)onSnapshotでリアルタイム反映
ホスティングGitHub PagesGitHub Pages(変更なし、SDKをCDN経由で読むだけ)
データの流れ
読み取り・人間の書き込み(直結)
ca.html(ブラウザ)→ Firestore SDK→ caThreads(Firestore)
Claudeレーンのみ(鍵検証が要るのでサーバー経由)
rbook/run ca→ Cloud Function(claude-lane)→ Admin SDK→ caThreads(Firestore)

baのab-board-api(Azure Functions)とは完全に別インフラになる。baとの一貫性より、ca自体の目的(干渉のリアルタイム観測)を優先する判断。

実装フェーズ
  1. P1
    Firebaseプロジェクト作成 新規GCPプロジェクト(または既存のAA_GOOGLE_CLIENT_ID所属プロジェクトに相乗り)にFirestore・Authenticationを有効化。
  2. P2
    Security Rules設計 読み取りは誰でも/書き込みはFirebase Auth済み(Googleログイン)のuidがtakashiのものだけ許可、種別ごとの制限もRules内で表現。
  3. P3
    Firebase Authentication設定 Google Sign-Inプロバイダを有効化。既存のOAuthクライアントを流用できるか、新規に切り直すかを確認。
  4. P4
    Cloud Function(claudeレーン専用) claude_key照合とAdmin SDK書き込みだけを行う最小HTTPSエンドポイントを1本実装・デプロイ。
  5. P5
    rbook CLI run_ca.pyはfirebase-admin(Python)を使い、サービスアカウント鍵ファイルで認証。現行のBA_CLAUDE_KEY方式(単純な共有文字列)とは鍵の運用形態が変わる。
  6. P6
    ca.html + Firestore SDK Firebase JS SDKを読み込み、直接read/write。onSnapshotでスレッド一覧をリアルタイム表示(手動リロード不要)。ab/src/index.htmlにnavカードを追加。
  7. P7
    運用監視の作り直し x2の既存ツール(expected_azure_tables.yml等)はAzure専用のため使えない。Firestoreコレクション構成やSecurity Rulesの期待状態を検証する仕組みを新規に用意する必要がある(現状ゼロから)。

P1〜P4(プロジェクト・認証・鍵レーン用Function)が先行必須。P5(CLI)とP6(ビューア)はその後なら並行/前後どちらでも着手可。P7は本番運用に入る前に着手。
